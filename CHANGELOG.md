# Changelog

Releases are published with generated notes on the repository's Releases page. This file records what an operator or app author needs to know when moving between versions. [docs/upgrading.md](docs/upgrading.md) has the upgrade steps and the data directory formats.

## Unreleased

- EXPERIMENTAL: `runtime = "wasip3-experimental"` in `spared.toml` for apps with `data = false`. One instance serves up to `[limits] concurrency` requests at once and interleaves them where they await (default and maximum `--max-app-concurrency`, 4 unless the operator sets 1 to 64). Off by default: the server serves these apps only with `spared serve --experimental-wasip3`, and otherwise refuses the deploy with 422 `experimental_runtime_off`. A data app is refused with `wasip3_data_refused`. `cpu_ms`, `max_outbound` and the log allowance stay per request, and `memory_mb` is one budget shared by the requests in flight. One trap fails every request in flight in the instance, compute in one request holds up the others, and a request past `deadline_ms` gets 504 while its task keeps running until the instance is dropped `deadline_ms` later. A task left running after its response keeps its place among `concurrency` until it ends or the instance is dropped, and a store allows 8,192 live stream, future and wait handles. A new template, `fetcher3`, uses the `wasip3` crate. `spared ps` labels these apps. They run on a second wasmtime engine with component-model async on, and wasip2 apps keep the engine they had. wasmtime marks its WASI 0.3 code not ready for production. New crate dependency: `futures` (already in Cargo.lock through wasmtime), and wasmtime's `task-group-hook` feature. See [docs/wasip3.md](docs/wasip3.md).
- Imports are matched with their version. An import without a version, or with a WASI version spared does not grant, is refused with `ungranted_import`. Before, a check by name prefix would have accepted, for example, `wasi:filesystem/types@0.3.0` under `data = true` and left the refusal to the link step.
- `may_create` now ends for every token of an app when the app is created, by any token or the admin token. Before, it ended only for the token that created the app, so a token minted for a free name stayed able to create it after the admin token or another token had, and a crash between a token's first deploy and the flag's write left it true. The flag is now written for every token of the name before the deploy commits, and a deploy whose write fails is refused with `token_write_failed`. Minting a token takes the app's name lock.
- A deploy by an app token no longer returns `component_reused`, which told it whether another app on the server runs the same code. The admin token still gets it. `component_sha256` stays in both, since it is the hash of the bytes the caller sent. A reused component still deploys faster, so the timing can tell the same thing.
- An app token with the `freeze` scope can no longer lift the operator's freezes. Before, it could thaw any freeze of its app, including one left by `spared move` or a stale upload (`remote_superseded`), and could freeze with kind `move`. Now an app token always freezes with a new kind, `app`, gets 403 `wrong_scope` if it names another kind, never replaces an existing freeze, and thaws only an `app` freeze. A `manual`, `move`, `remote_superseded` or `unknown` freeze needs the admin token. A move over an `app` freeze turns it into a `move` freeze.
- A token sent where a token id belongs is repeated nowhere. Before, `DELETE /v1/tokens/spt_...` wrote the whole token to the access log and echoed its first 40 characters in the `no_such_token` message, and other admin errors (`no_route`, `wrong_scope`) echoed the path. Now the access log shows `/v1/tokens/<redacted>` for any segment there that is not an id, and any admin path segment that holds `spt_` (also percent-encoded) is logged and echoed as `<redacted>`. `no_such_token` repeats the value only when it is a well-formed id.
- Lowering a CPU or egress budget no longer carries the old use as debt. Before, an app that used 500 MB under 1 GB an hour and was lowered to 1 MB an hour had its outbound calls refused for about 499 hours. A changed budget now keeps what was used up to its new size, so a lowered one starts empty and refills at the new rate within one window. Raising a budget still keeps what was used.
- `spared rm` no longer refills an app's CPU and egress budgets. Before, removing an app that had per-app limits and deploying it again under the same name started its counters over, so a platform's delete and recreate flow handed out a fresh egress hour and CPU bucket. The counters now stay while the override does. A server restart or `spared limits clear` still starts them over.
- Host backtraces are off by default. `spared` sets `RUST_BACKTRACE=0` and `RUST_LIB_BACKTRACE=0` for itself at start, unless `SPARED_ALLOW_HOST_BACKTRACE=1` is set, and child processes (cargo builds, the compile process) inherit that. Before, with `RUST_BACKTRACE=1` in the server's environment, an app that asked for the text of a failed stream (`wasi:io/error.to-debug-string`) got a host stack trace with host symbol names. That function now returns a fixed line, or the HTTP error code of a fetch, or the egress refusal's text, whatever the environment. Apps that printed that text see the fixed line instead. Three new escape cases cover it.
- Per-app limits set by the operator. `spared limits set <app>` (admin token only) gives one app a smaller data size (`--data-mb`) and entry count (`--entries`) than the server-wide caps, a CPU budget over time (`--cpu-percent` or `--cpu-ms-per-min`) and a budget for the bytes of its outbound HTTP calls (`--egress-mb-per-hour`: request and response heads, bodies and trailers). The smaller of the override and the server's cap is in force, so an override can only lower a cap. An app over its CPU budget gets 503 `cpu_budget_exhausted` with `Retry-After` for new requests, and an app over its egress budget sees its outbound calls fail with `egress_budget_exhausted`. `spared limits show` prints the limits in force and the use, `spared limits clear` removes them, and `spared ps --json` shows each app's `quota` and `data_entries` to the admin token. New admin routes: `GET`, `PUT` and `DELETE /v1/apps/{name}/limits`. App tokens get 403 `wrong_scope` on all of them. Limits are stored in `<data-dir>/limits/`, survive restarts, redeploys and `spared rm`, and `spared move` copies them to the target. CPU and egress use start over when the server restarts. Not bounded per app: memory below the manifest's `memory_mb`, disk and network bandwidth, and builds. No new crates. See [docs/operating.md](docs/operating.md#limit-each-app).
- Data directory format 2. A directory is stamped format 2 while any app has per-app limits, so a release from before them refuses to start on it with `data_dir_too_new` instead of serving those apps without their limits. Clearing the last one stamps it back to format 1, and a directory that never had limits stays at format 1. See [docs/upgrading.md](docs/upgrading.md#the-format-stamp).

- App tokens. `spared token create <app>` (with the admin token) makes a token that works only on that app's admin routes, within its scopes (`deploy`, `read`, `evict`, `backup`, `restore`, `freeze`, `rm`, default `deploy,read,evict`), and prints it once (`spt_` and 64 hex digits). The server keeps only its SHA-256, under `<data-dir>/tokens/`. `--expires 30d` sets a lifetime and `--name` a label. `--out FILE` writes the token to a new file with mode 0600 instead of printing it. `spared token list` and `spared token revoke <id>` manage them (a whole token given to `revoke` is turned into its id before anything is sent). An app token gets 403 `wrong_scope` for another app (the same answer whether it exists or not), for a missing scope, and for `/metrics`, `/v1/server`, `/v1/tokens`, code export and `spared move`, and 401 `token_expired` or `token_revoked` when it no longer works. A token made for a free name may create that app once. `spared rm` revokes the app's tokens. 30 wrong tokens in a minute from one address get 429 `auth_rate_limited` for every app token and unknown token from it; the admin token always works. A deploy checks its token again after the body is read, so one revoked meanwhile changes nothing. The access log records an app token's `token_id`. `SPARED_TOKEN` and `~/.spared/token` take an app token unchanged. The data directory format stays 1: an older release ignores `tokens/` and keeps working with the admin token. No new crates. See [docs/operating.md](docs/operating.md#give-each-app-its-own-token).

- `spared move <name> --to <admin URL>` moves an app to another server that backs up to the same bucket with the same key: it copies the app's code (the deployed wasm and `spared.toml`), freezes the app on the source, backs it up, fetches and compares that backup on the target, restores it there and thaws it. `--smoke-url` requests the app on the target afterwards, and `--dry-run` prints the plan. The target's token comes from `--to-token-file` or `SPARED_TARGET_TOKEN`. A failure before the restore thaws the source if this run froze it (`move_aborted`), a failure after it leaves the source frozen (`move_incomplete`), and running the command again picks up where it stopped. It never changes DNS and never deletes the app on the source. Not failover: both servers must be up. See [docs/operating.md](docs/operating.md#move-an-app-to-another-server).
- `spared freeze <name>` and `spared thaw <name>`. A frozen app answers public requests with 503 `app_frozen` and `Retry-After`, stays frozen across restarts, keeps every admin command, and refuses a deploy until it is thawed. `spared ps` shows the state `frozen`.
- Remote backup epochs. A restore from the bucket raises the server's epoch for the app to one above the highest in the bucket, and an upload that finds a higher epoch is refused with `remote_superseded` and freezes the app. This detects a second server writing the same app after the fact. It does not prevent it. Backups from before this change are epoch 1 and list and restore as before. The data directory format is unchanged, but an older release ignores the freeze marker: remove moved-away apps before going back to one.
- New admin routes: `POST /v1/apps/{name}/freeze` and `/thaw`, `GET /v1/apps/{name}/code`, `GET /v1/server`, and `PUT /v1/apps/{name}?frozen=move`.

- Off-machine backups. `spared serve --backup-to s3://<bucket>/<prefix>` uploads every backup to an S3-compatible bucket (`--backup-endpoint` for a store other than AWS S3, `--backup-region`, `--backup-addressing`), as one archive (tar, zstd, then ChaCha20-Poly1305 with the operator's key from `--backup-key-file`) and a manifest written last. Credentials come only from `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_SESSION_TOKEN` or their `_FILE` twins. The server refuses to start with `--backup-to` and no key unless `--backup-encryption off` is given, and `spared backup-key new` makes a key. `spared backup` waits for the upload and exits 1 with `remote_upload_failed` when it fails, keeping the local backup (`--no-wait` returns at once). `spared backups <name> --remote` lists the bucket, and `spared restore <name> --from remote:<id> --yes` downloads, verifies and unpacks a backup into a new local backup, then restores it. spared never deletes in the bucket: set a lifecycle rule. No new crates. Tested against an S3 stand-in in the test process, not against AWS S3, R2 or another real store. See [docs/operating.md](docs/operating.md#off-machine-backups).

- `spared setup` compiles SQLite for Wasm once and keeps the object in `~/.spared/lib` (`$SPARED_LIB_DIR` moves it, `SPARED_NO_SQLITE_CACHE=1` turns it off). The first build of an app reuses it: on a 4-core Linux VM the first `spared test` of a new notes app took 12 seconds instead of 57. A missing or damaged cache is not an error: the build compiles SQLite as before and keeps the object. The key covers the SQLite source, every compiler flag and the wasi-sdk version, and apps, `Cargo.toml` and `Cargo.lock` are unchanged. `spared doctor` reports the cache. An existing `~/.spared/target` rebuilds libsqlite3-sys and rusqlite once after the upgrade (3.9 seconds with the cache filled). See [docs/operating.md](docs/operating.md#the-sqlite-build-cache).

## 0.0.1-preview - 2026-11-11

The first public preview. Data directory format 1.

- `spared` is one binary: the server (`spared serve`) and the CLI (`setup`, `doctor`, `new`, `templates`, `test`, `deploy`, `dev`, `ps`, `logs`, `rm`, `backup`, `backups`, `restore`, `evict`, `bench`).
- Apps are Rust crates compiled to `wasm32-wasip2` components with SQLite inside; each runs in its own sandbox with one instance, its own data directory, and limits and grants from its `spared.toml`.
- `spared --version`; the server prints its version at start and reports it at `GET /healthz`.
- A request log on stdout (one JSON line per request, no query strings, headers or bodies; `--access-log off`), `GET /healthz` on the public listener, and `GET /metrics` (Prometheus text format) on the admin listener.
- The data directory carries a format stamp (`format.json`); a server that cannot read the format refuses to start with `data_dir_too_new` or `data_dir_too_old`.
- Per-app backups and restores with SHA-256 verification.
- Release binaries are built for Linux x86_64 and arm64 and macOS arm64 and x86_64 and published with `SHA256SUMS`, which the install script checks. Only Linux x86_64 is tested.
- Per-app resource caps so one app cannot take the server down: data size (`--max-app-data-mb`, 1024), entries under `/data` (`--max-app-entries`, 50000), open files (`--max-app-fds`, 64), four directory listings at once, log bytes per request and per second (`--max-log-kb-per-request`, `--max-log-kb-per-sec`; the log also rotates at 4 MiB), and requests running or waiting (`--max-app-queue`, 16; more get `503 app_busy` with `Retry-After`). An app that goes over one sees an ordinary error from the call.
- Backups keep holes in sparse files and refuse a data tree whose files add up to more than `--max-app-data-mb`.
- A server-wide budget for request bodies held in memory (`--max-body-buffer-mb`, 64); past it a request gets `503 server_busy` with `Retry-After`.
- After start the server reads stored components into the page cache in the background (`--prefetch-mb`, default 1024, `0` turns it off).
- One server per data directory: `spared serve` and `spared dev` lock `<data-dir>/.lock` and a second one exits with `data_dir_in_use`. A taken port exits with `address_in_use` before anything is written.
- Admin commands wait up to 2 s for a server that is still starting, so `spared serve &` followed at once by `spared deploy` works.
- A `fetch` entry with a scheme, path, port or user name, a bare `*`, or a private or loopback IP literal is refused as `bad_manifest`. A server that loads an app stored with such an entry skips that app and says why.
- Plain CLI errors read `error[kind]: message`. `spared dev` prints the `export SPARED_TOKEN=...` line for its own token. The blog template refuses to publish until its `TOKEN` constant is changed.
